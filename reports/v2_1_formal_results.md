## 结果解释与轨迹证据

- **工具协议恢复有效，但修复能力仍有限。** 60 项中全部解析并进入真实 Shell 执行链；相较旧 v2 的 60/60 `RepeatedFormatError`、零 Action，本轮无此格式错误。Shell 执行与评分链路有效，但三组仍只有 3–4 个正确补丁。
- **v2 反馈压缩减少了旧 Enhanced 的输入 Token。** 输入 Token 由 243,159 降至 221,146，少 22,013（−9.05%）；总 Token 下降 21,754（−8.72%）。但相对 Control，v2 输入 Token 仍高 4.19%、总 Token 高 3.55%。这是描述性成本结果，不能将差异完全归因于压缩模块，任务轨迹长度也不同。
- **重复失败没有下降。** 相对旧 Enhanced，v2 重复失败命令 89→87（少 2，−2.25%）；相对 Control，反而 71→87（增加 16）。v2 有 62 次守卫拦截，但拦截量不代表剩余重复命令下降，更不等同修复成功。
- **Verified-submit gate 确实阻止了未验证提交尝试。** gate 记录的 `submission_blocked` 为 Control 12、Enhanced 8、Enhanced v2 7；提交许可分别为 3、2、3。许可事件均由公开测试通过的当前源码哈希验证后产生。Enhanced E01 的轨迹显示先出现 pytest 失败，尝试提前提交被 gate 拒绝，后续公开测试通过后仍以 `LimitsExceeded` 结束，补丁独立评分正确但未正式提交。由于三组都启用 gate、没有无 gate 对照，不能声称它因果性地提升了提交率；本轮提交率也没有随算法组单调上升。
- **典型算法失败仍是反复试探与不完整修复。** Control B01 多次重复不可用的 `nano`、无效 `sed` 与失败 pytest；I01 对 `parse_bool` 反复叠加替换，测试持续失败。Enhanced E01 先产生不完整异常处理，随后某次修正通过公开测试，但预算/协议流程未能完成提交。Enhanced v2 B04 经历一次无效多行 `sed` 后改用追加式编辑，修复并通过测试、提交成功；v2 D02 的公开测试通过后仍未完成提交。上述均为所选轨迹中的具体例子，不代表每个任务的原因分布。
- **公共/隐藏评分一致性。** 三组各 4 个公开通过、4 个隐藏通过。Control 有 I02 仅公开通过、I01 仅隐藏通过，因此两者交集只有 3 个；Enhanced 和 Enhanced v2 的四个通过项均同时通过两套测试。正确率始终按两套都通过计算。

## 评分、预算和局限

每个任务均有独立 public/hidden evaluator 记录；评分不读取 Agent 自述。汇总器结果在运行时由批次写入：之后再次调用 `summarize_v2_results.py` 会因为目标汇总文件已存在而拒绝覆盖，这是保护行为，未重跑任务或覆盖结果。原始三组 summary/CSV 与逐任务记录保留。

运行记录中的平均 HTTP attempts 接近 12，但 `LimitsExceeded` 原因字段未细分，预算拒绝计数为零；不要把所有 Limit 终止都写成 attempt cap 命中。单次模型抽样、任务集在开发中构建、样本量 20、没有机制单独消融，都限制了因果归因。v1、v2 与 v2.1 条件/协议不同，不合并成功率。
